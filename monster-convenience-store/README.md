# 괴물 편의점

손님 카드를 좌우로 밀어 괴물 손님을 들이거나 돌려보내고, 손님이 바꾼 가게 환경(온도·바닥)에 맞춰 다음 손님을 고르는 세로 모바일 선택 퍼즐 프로토타입이다. 교대는 하나이고 손님은 고정된 10명이다.

- 파일: `index.html` 하나로 실행된다. HTML·CSS·JavaScript가 모두 들어 있고 외부 패키지·CDN·글꼴·이미지·음원·API 요청은 없다. 그림은 인라인 SVG로 그린다.
- 대상: 세로 휴대폰 브라우저(한 손 터치). 데스크톱에서는 같은 입력 논리를 마우스로 쓴다.

## 실행

- **데스크톱**: `index.html`을 브라우저로 연다.
- **휴대폰**: 이 폴더에서 `python3 -m http.server 8000`을 실행하고, 같은 LAN의 휴대폰에서 `http://<PC의 IP>:8000/`에 접속한다. 이미 쓰는 정적 파일 서버가 있으면 그것을 써도 된다. 서버는 파일을 전달할 뿐이고 게임은 네트워크를 쓰지 않는다.

## 조작

| 행동 | 입력 |
|---|---|
| 입장 | 카드를 오른쪽으로 밀기 또는 **입장 →** 버튼 (데스크톱은 → 키도 가능) |
| 거절 | 카드를 왼쪽으로 밀기 또는 **← 거절** 버튼 (데스크톱은 ← 키도 가능) |
| 다시 하기 | 교대가 끝난 뒤 **다시 하기** 버튼 |
| 규칙 다시 보기 | 오른쪽 위 **?** 버튼 (교대 중에만 활성) |

## 구현한 규칙과 수치

| 손님 | 요구(현재 상태에서 검사) | 효과(절대 대입, 언급 없는 축은 유지) |
|---|---|---|
| 꼬마 용 `dragon` | 바닥 마름 | 뜨거움 · 마름 |
| 눈사람 `snowman` | 뜨겁지 않음 | 온도만 차가움 |
| 비구름 `cloud` | 차가움 | 바닥만 젖음 |
| 증기 유령 `steam` | 젖음 | 뜨거움 · 마름 |
| 찜질 도깨비 `bath` | 뜨거움 | 온도만 차가움 |

- 고정 순서: `dragon, snowman, cloud, steam, snowman, bath, steam, dragon, dragon, bath`
- 시작 상태: 보통 · 마름, 판매 0, 불만 0, 인덱스 0
- 적합한 손님 입장: 판매 +1과 효과 적용. 부적합한 손님 입장: 불만 +1만(가게 그대로). 거절: 아무것도 바뀌지 않음. 모든 확정은 손님 한 명을 소비한다.
- 종료 판정: 불만 2회면 즉시 실패를 가장 먼저 판정한다. 그다음 열 번째 확정 뒤 판매 6건 이상이면 성공, 아니면 매출 부족 실패다.
- 스와이프: 수평 이동이 64 논리 px 이상이고 |dx| ≥ 1.5·|dy|인 정상 종료만 확정한다. 확정 뒤 0.3초 동안 입력을 잠근다.
- 다음 손님 예고 2명, 기준 화면 360×640 논리 px

## 자가검사

개발자 콘솔에서 실행한다. 정답 경로는 게임 화면에 표시하지 않는다.

- `index.html?selftest`로 열면 규칙 자가검사가 자동으로 돌고 콘솔에 `[괴물 편의점 자가검사] 통과 20 / 20`이 찍힌다.
- `MonsterStore.selfTest()`는 규칙 순수 함수 20항목을 검사한다. 손님 5종 × 상태 6가지 표, 전체 1024가지 선택 열거, 종료 우선순위, 재시작, 연쇄 없는 예고, 스와이프 판정 경계가 포함된다.
- `await MonsterStore.inputSelfTest()`는 실제 DOM에 합성 포인터 이벤트를 보내 확정 횟수를 센다(11항목). 추가 손가락, 합성 click, 짧은 드래그, pointercancel, 비율 미달, blur, 버튼 연타, 안내 창을 다룬다. **실행하면 진행 중인 교대를 처음부터 다시 시작한다.**

### 확인하지 않은 것

- **실제 기기는 확인하지 않았다.** 터치 검사는 모두 헤드리스 Chromium(Playwright 1.56, CDP 터치 에뮬레이션)에서 했다. iOS Safari와 Android Chrome에서 Pointer Events, pointercancel, 두 손가락 동작, 주소창 높이 변화는 납품 시 실제 기기로 시험해야 한다.
- **첫 플레이 이해 여부는 확인하지 않았다.** 실제 플레이어 테스트는 하지 않았다. 상태 열거는 인과의 논리 검사일 뿐 재미나 독창성을 증명하지 않는다.

### 플레이테스트에서 관찰할 것

- 다음 두 손님을 보고 지금 받을 수 있는 손님(특히 첫 꼬마 용)을 의도적으로 거절하는지
- 온도·바닥 두 상태축과 예고의 ‘입장 후 / 거절 후’ 표시를 읽고 그 이유를 말할 수 있는지
- 반증: 환경 효과 대신 순서 암기나 무작위 추측만으로 푸는지

## 화면 구성과 해석한 부분

- **위**: 판매(목표 6) · 불만(한계 2) · 남은 손님 카운터와 다음 손님 두 명. 각 예고 카드는 요구·효과를 보여 주고, `입장 후 ○/✕` · `거절 후 ○/✕`로 이번 선택 직후 ‘지금 상태라면’ 받을 수 있는지를 표시한다.
- **가운데**: 온도(차가움/보통/뜨거움)와 바닥(마름/젖음) 상태판, 그리고 가게 장면이다. 차가움은 고드름·서리·눈송이, 뜨거움은 김·나무 벽·온천 표시, 젖음은 물결·튜브·레인 로프(수영장), 마름은 타일로 그리고 바뀔 때 짧은 글이 뜬다. 상태는 색만이 아니라 글자·모양으로도 구별된다.
- **아래**: 현재 손님 카드(폭 280)와 큰 거절·입장 버튼. 카드에는 요구가 지금 맞는지와 입장 시 결과(판매 +1 → 바뀔 상태, 또는 불만 +1)가 적혀 있다.
- **예고 표시 방식(해석)**: 버튼만 쓰는 사람도 예고를 볼 수 있도록 `입장 후`와 `거절 후` 결과를 항상 함께 보여 준다. 카드를 끄는 동안이나 데스크톱에서 버튼에 마우스를 올리거나 키보드로 포커스하면 해당 쪽이 강조되고, 상태판에 점선 ‘예상’ 칸이 생긴다. 미리보기는 실제 상태와 카운터를 바꾸지 않는다.
- **추가 손가락(해석)**: 카드에서 시작한 첫 손가락만 추적한다. 다른 손가락의 누름·이동·뗌은 무시하고, 첫 손가락이 카드를 끄는 동안의 버튼 입력도 무시한다.
- **화면 맞춤**: 360×640 논리 화면을 비율대로 축소·확대한다. 폭에 맞춘 세로로 긴 휴대폰에서는 논리 높이를 최대 800까지 늘려 남는 공간을 가게 장면에 준다. 가로나 높이가 낮은 화면에서는 높이에 맞춰 줄이고, 휴대폰 가로 화면이면 옆 여백에 세로로 돌리라는 안내를 띄운다. 축소 때문에 버튼이 44 CSS px보다 작아지면 버튼의 논리 크기를 키운다.
- **종료 직후 0.3초**: 마지막 확정 직후의 입력이 바로 재시작으로 이어지지 않도록, 다시 하기 버튼도 확정 잠금 0.3초가 끝난 뒤에 받는다.
- 반응 연출(카드 날아감, 손님 등장, 말풍선, 입자)은 상태를 바꾸지 않고 입력 잠금을 늘리지 않는다. `prefers-reduced-motion`이면 줄어든다.
